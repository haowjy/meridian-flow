The Collab Domain, End to End

The collab domain turns Yjs updates into durable, fenced, attributed document history. Every content change is written to a Postgres journal before any Y.Doc applies it, so every in-memory Y.Doc can be thrown away and rebuilt. A writer's keystroke goes straight into the live document. An AI write goes either straight to live (direct mode) or into a per-Work draft that reaches live only when the writer applies it.

This page is a guided tour for building a mental model. It describes the code on this checkout and summarizes the deeper .context/ pages rather than repeating them. Code references are paths relative to apps/server/server/domains/collab/; lib/ means apps/server/server/lib/ and packages/ means the repo's packages directory. The draft versus live product model has its own page: the draft / live model.

1. What the domain is for

Collab owns durable Yjs infrastructure: the journals, checkpoints, authority heads and branches in Postgres, the server-side Y.Docs built from them, and the rules for admitting a change into them. It does not own editing semantics, the WebSocket shell, or files and folders. Four neighbors split the rest.

NeighborOwnsTalks to collab through
@meridian/agent-edit Model-facing read/write, the response buffer, write handles, and the cold undo/redo planner. It edits a memory-only runtime Y.Doc over host ports and never imports server code. Collab builds the cores and supplies the journal and coordinator ports. domain/agent-edit-runtime.ts, domain/thread-peer-core-pool.ts, packages/agent-edit/AGENTS.md
Hocuspocus transport Upgrade auth, room parsing, connection state, hook ordering, physical close codes, graceful drain. The CollabTransport methods: load, admit, store, drain. lib/yjs-ws-handler.ts, hocuspocus-persistence.ts
context domain documents rows, folder trees, paths and URIs, and the markdown_projection column. Seeds, content reads and writes, effective reads for a thread. Content is Yjs-canonical; the projection is a cache. ../context/adapters/context-fs/context-fs.ts
threads and runtime The frozen ThreadExecutionContext and the write tool wiring. agentEdit(context) picks the core; finalizeResponseCommit closes a reply. composition.ts, lib/model-tools/response-write-lifecycle.ts

The dependency direction is load-bearing: collab adapters import agent-edit, never the reverse. If agent-edit learned about Postgres or Works, it would stop being a reusable kernel and its cold reconstruction would start depending on server state it cannot replay.

2. The three kinds of Y.Doc

Every view of a document is a real Y.Doc, and changes move between them only by Yjs sync. That one rule is why a draft can fall behind live and catch up without a merge algorithm of our own.

Live documentWork draftThread peer
Durable form document_yjs_updates plus document_yjs_checkpoints, fenced by document_yjs_heads document_branches row (kind work_draft) with a full state snapshot, plus branch_write_journal rows document_branches row (kind thread_peer), upstream is the Work draft
Uniqueness One per document One active per (documentId, workId), shared by every thread in that Work One active per (documentId, threadId)
In memory The Hocuspocus room named by the document ID Branch-coordinator cache; Hocuspocus room branch:<id>:gen:<n> when a writer reviews it Branch-coordinator cache only; no room
Who writes Writers, direct-mode AI, push settlement, reversal Thread-peer commits, writer edits in the review room, live pulls The thread's agent-edit core

packages/database/src/schema/yjs.ts (unique indexes document_branches_active_work_draft and document_branches_active_thread_peer), hocuspocus-persistence.ts resolveBranchHocuspocusRoom (only work_draft branches get rooms)

How sync moves between them

  • Live to Work draft (pull). After a live writer update is journaled, a pull is scheduled with a 2 s debounce and a 10 s maximum; a review-room connection triggers one without waiting; a thread-peer write flushes one first. The pull replicates the live state into every active Work draft for that document and commits in its own root transaction, so a caller's rollback cannot undo it. domain/branch-pulls.ts, composition.ts (onLiveUpdatePersisted: branchPulls.scheduleLivePull), lib/yjs-ws-handler.ts onConnect
  • Work draft to thread peer (pull). Before a thread's first write to a document in a reply, pullThreadPeer flushes the live pull, then syncs the Work draft into the peer and returns the branch generation and watermarks the write is pinned to. domain/thread-peer-core-pool.ts write, domain/branch-pulls.ts
  • Thread peer to Work draft (commit). At response commit, the peer's delta is committed into the Work draft as one branch_write_journal row (source agent). domain/branch-agent-edit.ts createBranchAgentEditCoordinator
  • Work draft to live (push). Writer Apply, or an automatic push when the draft's push policy is auto. This is the only edge that needs consent. See section 7.

All branch Y.Docs are created with gc: false, and so are the Hocuspocus rooms (yDocOptions: { gc: false } in lib/yjs-ws-handler.ts). Reversal dependency checks, echo attribution and the stale-client fence all read tombstoned struct history; garbage collection would make those checks silently wrong.

3. Document authority

Each live document has one durable authority head, a row in document_yjs_heads. It answers one question for every writer and every journal read: which run of history is current? Three fields carry that.

FieldMeaningWhat it fences
authority_id Random UUID minted when the head is created. A generation replacement keeps it. Part of the journal's unique admission key and of every journal read and compaction filter.
authority_generation Starts at 1. Bumped only by a generation replacement (checkpoint restore). Journal reads replay only rows of the checkpoint's generation. Compaction and checkpoint manifests stay inside the current generation. Each live WebSocket connection is bound to the generation it opened under and is refused once the head moves.
next_admission_sequence Per-generation counter, incremented under the document mutation lock for each admission. Total order of admissions within a generation. A batch (for example a push's authored rows plus its reconcile row) shares one sequence and is ordered by batch_ordinal.

adapters/drizzle-document-authority-head.ts allocateDocumentAdmission, packages/database/src/schema/yjs.ts (document_yjs_updates_authority_admission unique index), adapters/drizzle-journal.ts read and compact

Every live journal append runs in a transaction that checks an agent write's grant, locks the bound grants' Works, then takes pg_advisory_xact_lock on document-mutation:<documentId>, then allocates the admission, inserts the row, and joins any unresolved push settlement for that document. That lock is the cross-process serialization point for live content; the in-process coordinator mutex is not (section 4). ../../shared/document-mutation-lock.ts, adapters/drizzle-journal.ts enterJournalSeam and appendUpdate

"Document authority" names the durable head and nothing else. The operation capabilities that admit content (admitFreshAuthorship, admitCertifiedMutation, replicateFrozenIdentity, replaceAuthorityGeneration) are the document mutation policy, and an in-memory room is the live document. domain/document-mutation-policy.ts, document authority and schema

What a restore does to the head

Restoring a checkpoint cannot be a Yjs apply: applying old state to the current doc merges with it instead of replacing it. So a restore installs the checkpoint as a new generation.

  1. Under the document mutation lock, check the head is still at the expected generation, refuse with authority_head_busy while any push settlement for the document is not completed, and refuse with checkpoint_incomplete if the checkpoint lacks state or an attribution manifest.
  2. Copy the checkpoint into a new document_yjs_checkpoints row at generation + 1, with the manifest floor reset to null, and move the head: generation + 1, next_admission_sequence = 1.
  3. Disconnect the old generation: record the retired room's state vector, close its connections, and drop the room without checkpointing it. A stale session's next frame is refused as stale-durable-authority-generation, and a frame replaying retired structs is refused as retired-durable-authority-generation.

adapters/drizzle-document-authority-head.ts replaceDocumentAuthorityHeadGeneration, domain/document-mutation-policy.ts replaceAuthorityGeneration, hocuspocus-persistence.ts disconnectLiveGeneration and admitLiveWriterUpdate

On this checkout, CollabDomain.restore is wired to that path in composition.ts, but no route or service outside collab calls it.

4. The writer write path

A writer's keystroke is durable in Postgres before Hocuspocus applies it, broadcasts it, or acknowledges it. The transport's awaited beforeSync hook is the admission point.

  1. Connect. onConnect authenticates, checks document access, requires live manifest membership for a live room, runs the schema fence (section 9), and records the admission target. For a live room the target captures the current authority generation; every later frame on that connection is checked against it. lib/yjs-ws-handler.ts classifyYjsConnectionAdmission
  2. Admit. beforeSync calls admitLiveWriterUpdate, which runs the shared admitWriterUpdate sequence: fence, containment, fresh authorship, append. hocuspocus-persistence.ts, domain/document-mutation-policy.ts
  3. Append. appendWriterUpdate opens its own transaction, locks the document, allocates an admission, inserts the row with origin_type = human, and calls joinAdmissionWithinTx so any in-flight push settlement sees this edit. adapters/drizzle-journal.ts
  4. Apply and broadcast. Hocuspocus applies the frame to the room only after the hook resolves, then broadcasts and acknowledges it.
  5. Afterwards. The live-to-draft pull is scheduled; an admitted sync step 2 (a reconnect carrying offline edits) is queued for offline reconciliation, which adds writer blocks lost to a merged agent deletion to that agent turn's change trail; Hocuspocus onStoreDocument (2 s debounce, 10 s maximum, and last disconnect) queues a checkpoint. hocuspocus-persistence.ts persistConnectionUpdate and storeHocuspocusDocument, domain/offline-reconciliation.ts

A failed admission closes the socket through the raw peer with 1013 writer-journal-admission-failed. Throwing alone is not enough: Hocuspocus swallows a thrown error's code, so only the direct peer close preserves it. WebSocket concurrency

Journal first. Novel content is durable before any Yjs apply, broadcast, or ack. If it were applied first, a crash or failed insert would leave other clients holding prose that no durable record contains, and the next cold load would silently lose it.

Reserved client IDs and the provenance namespace

Yjs client IDs 0 through 999 belong to server-authored streams; the agent-edit reversal writer uses 999. Every server Y.Doc is built with createCollabYDoc, which redraws until its ID is outside that band. A writer frame carrying a struct from the band is rejected, the document is marked so the next room checkpoint is skipped (the rejected struct may still sit in memory), and an invariant event is emitted. If a client could author under a reserved ID, two writers would share one client ID, which breaks the Yjs assumption that one ID has one writer and would let a client forge reversal history. packages/prosemirror-schema/src/index.ts RESERVED_CLIENT_ID_MAX, hocuspocus-persistence.ts rejectReservedClientIdUpdate

The Y.Map __meridian_provenance_targets_v1 is the reserved provenance namespace. The server writes certified target-to-root lineage facts there so moved or restored prose keeps its original first-birth attribution. A writer update that inserts into, deletes from, or anchors inside that map is rejected before append. A client able to edit it could rewrite whose prose is whose, and with it which edits count as swept writer work. domain/provenance.ts PROVENANCE_TARGETS_TYPE and validateClientUpdateAdmission

The WebSocket concurrency fence (LOCK-WS)

withDocument() on the live coordinator is an in-process mutex over coordinator callers. It does not stop Hocuspocus from applying a writer frame to the same Y.Doc while a coordinator callback is awaiting a database call. So any server-side apply that follows an await must re-check the live document and apply in one synchronous block with no await between them. agent-edit's applyCommittedUpdateWithRecheck is that block for response commits and reversal; push settlement uses a full-state fingerprint compare plus the writer-ingress generation inside its completion fence. adapters/hocuspocus-coordinator.ts, packages/agent-edit/src/tool/mutation-commit.ts, domain/branch-push-transition.ts completeUnderFence, WebSocket concurrency

The review-room variant (writer edits in a Work draft)

A draft review room is an ordinary collaborative room; the writer is one more peer. The transport first enforces the stale-client handshake: a sync step 1 whose state vector reaches into clocks discarded by a branch reset closes with 4205 branch-stale-doc, and no update is accepted before that handshake passes. Admission then runs the same sequence against one locked branch snapshot: the branch must be an active work_draft at the room's generation and the room must contain the snapshot; then containment, fresh authorship, and a snapshot compare-and-set plus a branch_write_journal row with source writer. A failure closes with 1008 branch-update-admission-failed. Branch rooms never re-persist in onStoreDocument; every branch mutation is already durable.

lib/yjs-ws-handler.ts enforceBranchHandshake and admitBranchSync, domain/branch-coordinator.ts commitWriterUpdate, hocuspocus-persistence.ts admitBranchWriterUpdate and storeHocuspocusBranch

5. The AI write path

An AI write is staged in agent-edit's runtime Y.Doc for the length of a model response, then committed in three phases. Where the commit lands depends on the thread's Work.

ModeChosen whenCoreLands in
Direct The Work's aiWriteMode is direct (Auto-apply), so draftOwner === null. This includes No Work. The live utility core The live journal and live room, at response commit
Draft aiWriteMode is draft The thread's thread-peer core The Work draft; live only after a push

composition.ts (agentEdit: (context) => context?.draftOwner === null ? runtime.liveUtilityCore : agentEdit), ../threads/domain/thread-execution-context.ts

The three commit phases

  1. Preflight. Under the coordinator lock, capture what changed concurrently since the model's read. This feeds the echo the model sees; it never vetoes the write.
  2. Journal acceptance. Direct mode calls appendBatch on the live journal: one transaction that locks every touched document in sorted order, allocates one admission per document, inserts the agent rows and their agent_edit_mutations rows (which carry the w<N> handles). Draft mode's journal only stages the entries in memory; their durable home is the branch commit in phase C.
  3. Apply. Under the coordinator lock, applyCommittedUpdateWithRecheck re-captures concurrency and applies the merged update in one synchronous block. In direct mode that target is the live room. In draft mode it is the thread peer, and the thread-peer coordinator then commits the peer's delta into the Work draft (snapshot compare-and-set plus one branch_write_journal row, through admitCertifiedMutation when the write carries a semantic edit IR).

packages/agent-edit/src/tool/response-committer.ts, adapters/drizzle-journal.ts appendBatch, domain/branch-agent-edit.ts, domain/branch-coordinator.ts commitSyncFromDoc

Draft-mode commits run inside one Drizzle transaction per reply, with process-local effects (branch cache updates, watermarks, response ownership) enlisted as participants that commit or abort with it. A failed multi-document reply leaves nothing behind. Direct mode commits inside the live core instead. domain/thread-peer-core-pool.ts commitResponse, domain/response-transaction.ts, domain/response-write-finalizer.ts

After commit, finalizeResponseCommit records late-sweep and awareness notices, checkpoints each touched thread peer (draft mode), and refreshes the markdown projection for each document (section 10). If the Work draft's push policy is auto, a push is scheduled after the database commit. domain/response-write-finalizer.ts, domain/branch-agent-edit.ts scheduleAutoPushAfterCommit

Merges are trusted. Destructive effects become marks, receipts and trail evidence, never a veto on a valid Yjs merge. Undo is the recovery. Adding an approval gate here would refuse the writer's own instruction to the AI.

Settlement: how a push reaches live

A push (Apply or automatic) is a staged, fenced transition so that warm and cold execution produce the same live document.

  1. Lock. Branch locks in branch-ID order, then live coordinator locks in document-ID order. The first thing done inside each live lock is to capture the complete Yjs state: the lock cut.
  2. Durable commit. One transaction writes push_lineage (publication identity and idempotency key), the branch_push_settlement_outbox row (lock cut, push update, trail seed, claim), and the required change trail.
  3. Settle. Drain writer admissions that started before this point, reload the outbox (including any writer edits joined after the cut), rebuild the final pre-push document from the lock cut plus those post-cut updates, and settle the trail.
  4. Complete under the fence. In one transaction under the document mutation lock: append the branch's exact authored rows with their original attribution plus one reconcile row carrying the whole push update, re-derive the projection from the durable journal, then, still synchronously, compare the live room's full-state fingerprint to the rebuilt pre-push document and apply the push only if they match. A newer writer admission or mismatch means retry.

domain/branch-push.ts, domain/branch-push-transition.ts, adapters/drizzle-branch-push.ts, adapters/drizzle-pending-settlement.ts withCompletionFence and completeStagedPush

The reconcile row exists because the active authored rows alone can omit causal dependencies of the branch state being published; replaying only them cold would not reproduce the merged live document. It is coverage, not an author: dependency checks ignore it and it is never a reversal target. A crash after the durable commit leaves a pending outbox row that the recovery lane (recoverPendingLiveSettlements, run by the change-trail worker) completes with the same code path. Depth lives in push settlement and change trail.

The change trail and receipts

  • Change trail. The sole durable publication record: one folded set of before/after block changes per turn (or one shared trail per thread), keyed by Yjs {clientID, clock} identity. It is written by push commit and settlement, and by offline reconciliation. A direct-mode AI write does not write a trail on this checkout. adapters/drizzle-branch-push.ts persistRequiredTrail, domain/offline-reconciliation.ts, adapters/drizzle-change-trail-aggregate.ts
  • Turn trail work. A database trigger enlists every turn-owned branch_write_journal row in turn_trail_work. The change-trail worker retries auto-policy pushes from it and marks work no_op when the push policy is manual or the turn ended error or cancelled. packages/database/src/migrations/0000_baseline.sql enlist_turn_trail_work, adapters/drizzle-turn-trail-work.ts, adapters/change-trail-worker.ts
  • Receipts. A turn's receipt chip is server-derived: for live writes from agent_edit_mutations plus agent-edit's planUndo/planRedo; for draft writes from the branch journal and the branch reversal planner. Receipt Undo/Redo is the only reversal authority for AI changes; trail evidence is read-only. adapters/drizzle-turn-receipt.ts, domain/turn-receipt.ts

6. The journal and reconstruction

The live journal is an append-only list of Yjs updates per document, plus checkpoints that cache a prefix of it. A live Y.Doc is always "the newest checkpoint plus every later row of the same generation".

TableHolds
document_yjs_updatesOne row per admitted update: bytes, authority ID, generation, admission sequence, batch ordinal, origin (human, agent, system, reconcile), actor user or turn, authoring response, reversal actor.
document_yjs_checkpointsFull encoded state at up_to_seq, its authority generation, and an attribution manifest that freezes first-birth attribution so compaction cannot lose it.
document_yjs_headsThe authority head, plus the schema stamp and latest checkpoint and state vector.
agent_edit_mutations, document_yjs_reversals, document_yjs_reversal_opsWrite handles and reversal state and lineage, keyed to update row IDs.

packages/database/src/schema/yjs.ts

A writer's typing produces roughly one row per keystroke; row counts are not semantic edits. Reconnect frames the room already contains are acknowledged without a row.

Where checkpoints come from

  • Seed. A new document's first content is installed as an up_to_seq = 0 checkpoint with no journal rows. Seeding is initialize-only; a later attempt on a document with any admission or checkpoint is a successful no-op. adapters/drizzle-journal.ts createServerDocumentLifecycle, domain/markdown-document.ts seedFromMarkdown
  • Room store. Hocuspocus onStoreDocument snapshots the room and the latest row ID, then writes the checkpoint after the caller's transaction commits (dropped on rollback or when the generation was retired), one queued write per document, newest wins. A checkpoint at a cut no newer than the existing one is skipped. hocuspocus-persistence.ts storeHocuspocusDocument, adapters/drizzle-journal.ts checkpoint
  • Explicit. CollabDomain.checkpoint(documentId, reason). checkpoints.ts
  • Compaction. journal.compact(docId, before) folds the contiguous prefix of current-generation rows older than before into a compact checkpoint, deletes those rows and their reversal ops, and expires reversals created before the cutoff. It is implemented and tested, but no production scheduler calls it on this checkout, so live rows are never deleted. adapters/drizzle-journal.ts compact

The rule for every checkpoint writer: it may under-claim but must never over-claim. A row at or below up_to_seq is never replayed again, so if the state lacked it the row is lost; a row above it replays harmlessly on top. That is why the writers read up_to_seq before encoding the state. hocuspocus-persistence.ts storeHocuspocusDocument, checkpoints.ts checkpoint

adapters/document-loader.ts loadDocumentState, adapters/drizzle-journal.ts read, adapters/hocuspocus-coordinator.ts applyMissing, domain/branch-coordinator.ts materialize and runWithRetry

The coordinator heal matters: every withDocument call opens the room, re-reads the journal, and applies whatever durable rows the room is missing before the callback runs. A row that was journaled but never applied to a warm room therefore heals on the next server touch, and a cold room simply replays it.

Historical and reconstruction reads

journal.read takes optional since and until row bounds; with until it picks the newest checkpoint at or before that row so a historical read never sees later edits. No production caller passes until on this checkout. readForReconstruction (used by cold undo/redo and echo attribution) instead picks the newest checkpoint strictly below the earliest retained row, so it replays every retained row that reversal might target. Settlement rebuilds its historical "final pre-push" document from the outbox's own lock cut plus joined updates, never from the current room.

adapters/drizzle-journal.ts reconstructionCheckpoint, domain/branch-push-transition.ts materializeFinalPrePush

7. Branches: pulls, pushes, Apply, Discard

Branch mechanics are covered in depth by branch model and records and the product shape by the draft / live model. The points below are the ones that change how you reason about edits here.

  • Pulls are replication, not authorship. A live pull uses replicateFrozenIdentity on a frozen copy of live, so pulled structs keep their original Yjs identities and attribution. Pulls take the snapshot compare-and-set without the Work lifecycle lock because they create no reviewable edit, and they publish the delta to an open review room through the normal branch update publisher. domain/branch-coordinator.ts pullFromDoc
  • Apply publishes the whole current branch. DraftApplyRequest is { draftId }. The server pushes every reviewable row of the current generation, including writer edits made after the preview was rendered. Preview revisions are evidence, not command scope. A new document drafted only in the Work is pushed together with its project-manifest entry in one batch. packages/contracts/src/drafts/review.ts, domain/work-draft-review-service.ts applyWorkDraft, domain/branch-push.ts pushToLiveWithManifestEntry
  • No stale-Apply refusal on this checkout. Apply carries no live-head token; a push integrates through Yjs against whatever live holds at the lock cut. The settlement fence protects concurrent writer edits from being lost, not the writer from applying against a live they have not seen.
  • Discard has two shapes. Full Discard resets the content branch to live in one Work-locked transaction (and removes a draft-only document's manifest entry); it bumps the branch generation, records the discarded state vector, and requires the Work to be active. Selective Discard removes the rows of server-vended discard classes chosen from the preview; the client never reconstructs turns. adapters/drizzle-work-draft-discard.ts, domain/work-draft-review-service.ts discardWorkDraft, domain/branch-review-operations.ts
  • Generation is branch identity. A reset bumps document_branches.generation, closes the old room, and its clients are fenced by the 4205 handshake. Thread-peer and Work-draft generations are separate counters; see TODO. domain/branch-coordinator.ts persistReset, adapters/hocuspocus-binding.ts closeBranch

Echo attribution

When the model writes, its result echoes what others changed in the same blocks since its read. In draft mode the thread-peer coordinator builds that echo from durable evidence only: Work-draft journal rows after the thread's concurrent-journal watermark, plus live journal rows after the live sequence captured at pull time. It replays them over the peer's baseline and attributes each touched block to an agent turn or a writer by block coverage; whatever the rows do not explain becomes an unattributed human residual. Memory-only maps are never an attribution source, so a restarted process echoes the same thing. The watermark advances only when the surrounding branch write commits.

domain/branch-agent-edit.ts concurrentUpdatesSince and partitionConcurrentUpdates, domain/branch-update-attribution.ts

8. Reversal

Undo and Redo of AI writes are planned by agent-edit and authorized by collab's durable state. There is no hot undo stack: every reversal is a cold reconstruction from the journal. agent-edit replays the retained rows into a fresh Y.Doc, tags only the target write's rows for a local Y.UndoManager, runs undo or redo, and extracts the resulting update, which is then admitted like any other write under the reserved client ID 999. packages/agent-edit/.context/write-architecture.md, domain/thread-peer-core-pool.ts (undoClientId: AGENT_EDIT_UNDO_CLIENT_ID)

  • Which journal. While the current Work-draft generation holds agent rows for the thread, reversal is branch-scoped and writes a system row into the branch journal. Otherwise, including after Apply empties the branch, it routes to the live utility core. domain/thread-peer-core-pool.ts reversalCoreFor, domain/branch-reversal-history.ts
  • The live guard is intrinsic. persistUndo re-runs the dependency check and the writer watermark inside the append transaction under the document mutation lock, so a writer edit admitted between planning and persisting turns the result into cant_undo_dependent instead of undoing over it. Branch reversal uses the branch generation, journal watermark and status revision under the snapshot compare-and-set instead. adapters/drizzle-journal.ts persistUndo, adapters/drizzle-branches.ts commitBranchMutation
  • Writer rows withdraw redo; agent and system rows do not. One planner (planUndo, planRedo) drives both the receipt's availability and the command, so they disagree only across a race, and the endpoint returns those races as HTTP 200 outcomes (nothing_to_undo, cant_undo_dependent, partial, and so on).
  • Turn reversal is atomic. Branch and live changes persist in one transaction; a mixed success and no-op across documents aborts all of it. Room application, broadcasts and projection refresh run only after commit. domain/turn-reversal-service.ts

Full contracts: reversal.

9. Schema fence and repair

A Y.Doc's bytes only make sense under the ProseMirror schema that wrote them. The fence stops a client or server from replaying a document under a schema that would corrupt it; repair keeps a document usable when content does not fit.

The fence

  • Heads and branch rows carry a packed (major, minor, patch) stamp, raised with greatest() so a rolled-back server can never lower it.
  • On connect, per connection (Hocuspocus deduplicates loads): if the server's major differs from the head's, close 4407 document-schema-stale; else if the client's (major, minor) is behind the head, close 4406 client-schema-superseded. Patch never gates. An unstamped head passes.
  • Every journal read asserts the head's major matches the server and throws DocumentSchemaMajorMismatchError otherwise; the load hook turns that into the same 4407 close as a race backstop.

lib/yjs-ws-handler.ts classifyYjsConnectionAdmission, packages/prosemirror-schema/src/collab-schema-version.ts, domain/stale-schema.ts, adapters/drizzle-journal.ts upsertHead and assertReadableHead

Coherence and repair

  • One engine. Every seed, write and serialization goes through domain/markdown-document.ts, which resolves the document's filetype first (markdown codec for documents; one verbatim code_block for code). Hand-built fragment content could produce state the client's schema would normalize away.
  • Serialization never mutates its input. Projection runs on a private gc: false clone. If normalization changes that clone, a collab.schema serialize.anomaly_observed event is emitted (schema version and counts, never prose) and serialization continues.
  • Client repairs merge. When y-prosemirror repairs invalid content in the editor, the repair is an ordinary writer update that goes through the path in section 4; the client's schema repair witness reports it to the writer and never blocks it. apps/app/src/core/editor/schema-repair-witness.ts

Depth: document authority and schema.

ContextFS.search reads content through collab: live markdown for ordinary scopes, and the thread's effective view (thread peer or Work draft) for a manuscript search inside a thread. So search is current even when the projection is stale. The full-text and trigram indexes on markdown_projection exist in the schema, but no query on this checkout uses them. ../context/adapters/context-fs/context-fs.ts search, packages/database/src/schema/content.ts
  • Readers that do use it: repairing a tracked document that is missing from manifest membership seeds Yjs from the projection (a no-op when Yjs state already exists, since seeding is initialize-only); the download route falls back to it when the Yjs read fails; upload identity lookups return it. ../context/adapters/context-fs/context-fs.ts repairTrackedDocument, ../../routes/api/documents/[documentId]/download.get.ts, ../context/uploads/upload-identity.ts

So on this checkout a stale projection is visible through the download fallback and upload identity, not through search or the editor.

11. The composition root

createCollabDomain in composition.ts is wiring only: it builds adapters, builds domain services with required dependencies, and returns the facade. Behavior lives in domain/; collab-facade.ts only spreads the service groups into CollabDomain. The order of construction follows the dependency graph.

  1. Persistence and live transport. The Drizzle journal and lifecycle; a late-bound Hocuspocus binding (the gateway binds itself after construction); the live coordinator over it.
  2. Branches. One BranchCriticalSections (the only owner of the branch mutex, shared by store, coordinator, push, review and discard so lock order stays global); the branch store, coordinator and pull service.
  3. Runtime. createAgentEditRuntime builds the markup codec exactly once with the injected DocumentLinkScopes, the schema-aware markdown engine, and the live utility core, each spelling links and image sources through the operation's prepared link scope. A second mdxCodec(...) elsewhere would spell stored hrefs instead of current paths.
  4. Settlement and push. Pending-settlement store, push-commit store, change-trail writer, writer-ingress binding (bound to the Hocuspocus persistence barrier once that exists), push service, review operations.
  5. AI cores. The thread-peer core pool over the live utility core, branch services and the response-transaction hooks.
  6. Transport persistence. Hocuspocus persistence wired to the journal, the authority-generation reader, offline reconciliation, and scheduleLivePull.
  7. Read models and commands. Response finalizer, Work-draft review service, effective reader, checkpoint service with generation replacement, receipt lineage, turn reversal service; then the facade, whose agentEdit(context) selects the core per call.

Optional notices and the thread-context resolver are replaced by declared stubs in one place (adapters/declared-stubs.ts) instead of optional fields that would let a path silently skip a required operation. The in-memory composition (adapters/in-memory/composition.ts) builds the same interfaces for tests. Rules for this file are in CONTEXT.md.
