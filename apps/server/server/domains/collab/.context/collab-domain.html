The Collab Domain, End to End

The collab domain turns Yjs updates into durable, fenced, attributed document history. Every content change is written to a Postgres journal before any Y.Doc applies it, so every in-memory Y.Doc can be thrown away and rebuilt. A writer's keystroke goes straight into the live document. An AI write goes either straight to live (direct mode) or into a per-Work draft that reaches live only when the writer applies it.

This page is a guided tour for building a mental model. It describes the code on this checkout and summarizes the deeper .context/ pages rather than repeating them. Code references are paths relative to apps/server/server/domains/collab/; lib/ means apps/server/server/lib/ and packages/ means the repo's packages directory. The draft versus live product model has its own page: the draft / live model.

1. What the domain is for

Collab owns durable Yjs infrastructure: the journals, checkpoints, authority heads and branches in Postgres, the server-side Y.Docs built from them, and the rules for admitting a change into them. It does not own editing semantics, the WebSocket shell, or files and folders. Four neighbors split the rest.

NeighborOwnsTalks to collab through
@meridian/agent-edit Model-facing read/write, the response buffer, write handles, and the forward-inverse planner behind model revert and failed-reply rollback. It edits a memory-only runtime Y.Doc over host ports and never imports server code. Collab builds the cores and supplies the journal and coordinator ports. domain/agent-edit-runtime.ts, domain/thread-peer-core-pool.ts, packages/agent-edit/AGENTS.md
Hocuspocus transport Upgrade auth, room parsing, connection state, hook ordering, physical close codes, graceful drain. The CollabTransport methods: load, admit, store, drain. lib/yjs-ws-handler.ts, hocuspocus-persistence.ts
context domain documents rows, folder trees, paths and URIs, and the markdown_projection column. Seeds, content reads and writes, effective reads for a thread. Content is Yjs-canonical; the projection is a cache. ../context/adapters/context-fs/context-fs.ts
threads and runtime The frozen ThreadExecutionContext and the write tool wiring. agentEdit(context) picks the core; finalizeResponseCommit closes a reply. composition.ts, lib/model-tools/response-write-lifecycle.ts

The dependency direction is load-bearing: collab adapters import agent-edit, never the reverse. If agent-edit learned about Postgres or Works, it would stop being a reusable kernel and its cold reconstruction would start depending on server state it cannot replay.

2. The three kinds of Y.Doc

Every view of a document is a real Y.Doc. A thread peer syncs with its Work draft by Yjs. A Work draft and live do not: nothing relates live's items to the draft's, so the draft catches up to live by a content rebase and reaches live by a content merge. Either way a draft can fall behind live and catch up without a refusal.

Durable form document_yjs_updates plus document_yjs_checkpoints, fenced by document_yjs_heads document_branches row (kind work_draft, the item's text branch) with a full state snapshot, plus branch_write_journal rows. Its Y.Doc holds two fragments: prosemirror (what the writer and the AI edit) and the server-owned review_base (live's text as of base_revision) document_branches row (kind thread_peer), upstream is the Work draft

How sync moves between them

  • Live to Work draft (rebase). After a live writer update is journaled, a catch-up is scheduled with a 2 s debounce and a 10 s maximum; a review-room connection awaits one before frames are admitted; a thread-peer write flushes one first. For a Work draft the catch-up is the rebase (draft-rebase.ts): a three-way content merge of review_base, live and the draft, written into both fragments in one transaction as server client 1 and persisted by one branch compare-and-set that also records base_revision and has_effect. The rebase takes live's content and revision from one certified live cut (LiveCut), so a revision never certifies text it has not read. It waits while a settlement batch on the document is pending or blocked, and a failure fails the pull as a typed outcome rather than retrying unchanged inputs. domain/branch-pulls.ts, domain/draft-rebase.ts, adapters/drizzle-live-cut.ts, composition.ts (onLiveUpdatePersisted: branchPulls.scheduleLivePull), lib/yjs-ws-handler.ts onConnect
  • Work draft to thread peer (pull). Before a thread's first write to a document in a reply, pullThreadPeer flushes the live catch-up, then syncs the Work draft into the peer by Yjs and returns the watermarks the write is pinned to. The pull copies the draft's whole encoded doc, base included; the peer never advances that base. domain/thread-peer-core-pool.ts write, domain/branch-pulls.ts
  • Thread peer to Work draft (commit). At response commit, the peer's delta is committed into the Work draft as one branch_write_journal row (source agent). domain/branch-agent-edit.ts createBranchAgentEditCoordinator
  • Work draft to live (content Apply). The writer's Apply. This is the only edge that needs consent, and it is a merge, not a copy. See section 7.

All branch Y.Docs are created with gc: false, and so are the Hocuspocus rooms (yDocOptions: { gc: false } in lib/yjs-ws-handler.ts). Revert dependency checks, echo attribution, the review projection and late-peer recovery all read tombstoned struct history; garbage collection would make those checks silently wrong.

3. Document authority

Each live document has one durable authority head, a row in document_yjs_heads. It answers one question for every writer and every journal read: which run of history is current? Three fields carry that.

FieldMeaningWhat it fences
authority_id Random UUID minted when the head is created. A generation replacement keeps it. Part of the journal's unique admission key and of every journal read and compaction filter.
authority_generation Starts at 1. Bumped only by a generation replacement (checkpoint restore). Journal reads replay only rows of the checkpoint's generation. Compaction and checkpoint manifests stay inside the current generation. Each live WebSocket connection is bound to the generation it opened under and is refused once the head moves.
next_admission_sequence Per-generation counter, incremented under the document mutation lock for each admission. Total order of admissions within a generation. A batch (for example a push's authored rows plus its reconcile row) shares one sequence and is ordered by batch_ordinal.

adapters/drizzle-document-authority-head.ts allocateDocumentAdmission, packages/database/src/schema/yjs.ts (document_yjs_updates_authority_admission unique index), adapters/drizzle-journal.ts read and compact

Every live journal append runs in a transaction that checks an agent write's grant, locks the bound grants' Works, then takes pg_advisory_xact_lock on document-mutation:<documentId>, then allocates the admission, inserts the row, and joins any unresolved push settlement for that document. That lock is the cross-process serialization point for live content; the in-process coordinator mutex is not (section 4). ../../shared/document-mutation-lock.ts, adapters/drizzle-journal.ts enterJournalSeam and appendUpdate

"Document authority" names the durable head and nothing else. The operation capabilities that admit content (admitFreshAuthorship, admitCertifiedMutation, replicateFrozenIdentity, replaceAuthorityGeneration) are the document mutation policy, and an in-memory room is the live document. domain/document-mutation-policy.ts, document authority and schema

What a restore does to the head

Restoring a checkpoint cannot be a Yjs apply: applying old state to the current doc merges with it instead of replacing it. So a restore installs the checkpoint as a new generation.

  1. Under the document mutation lock, check the head is still at the expected generation, refuse with authority_head_busy while any push settlement for the document is not completed, and refuse with checkpoint_incomplete if the checkpoint lacks state or an attribution manifest.
  2. Copy the checkpoint into a new document_yjs_checkpoints row at generation + 1, with the manifest floor reset to null, and move the head: generation + 1, next_admission_sequence = 1.
  3. Disconnect the old generation: record the retired room's state vector, close its connections, and drop the room without checkpointing it. A stale session's next frame is refused as stale-durable-authority-generation, and a frame replaying retired structs is refused as retired-durable-authority-generation.

adapters/drizzle-document-authority-head.ts replaceDocumentAuthorityHeadGeneration, domain/document-mutation-policy.ts replaceAuthorityGeneration, hocuspocus-persistence.ts disconnectLiveGeneration and admitLiveWriterUpdate

On this checkout, CollabDomain.restore is wired to that path in composition.ts, but no route or service outside collab calls it.

4. The writer write path

A writer's keystroke is durable in Postgres before Hocuspocus applies it, broadcasts it, or acknowledges it. The transport's awaited beforeSync hook is the admission point.

  1. Connect. onConnect authenticates, checks document access, requires live manifest membership for a live room, runs the schema fence (section 9), and records the admission target. For a live room the target captures the current authority generation; every later frame on that connection is checked against it. lib/yjs-ws-handler.ts classifyYjsConnectionAdmission
  2. Admit. beforeSync calls admitLiveWriterUpdate, which runs the shared admitWriterUpdate sequence: fence, containment, fresh authorship, append. hocuspocus-persistence.ts, domain/document-mutation-policy.ts
  3. Append. appendWriterUpdate opens its own transaction, locks the document, allocates an admission, inserts the row with origin_type = human, and calls joinAdmissionWithinTx so any in-flight push settlement sees this edit. adapters/drizzle-journal.ts
  4. Apply and broadcast. Hocuspocus applies the frame to the room only after the hook resolves, then broadcasts and acknowledges it.
  5. Afterwards. The live-to-draft pull is scheduled; an admitted sync step 2 (a reconnect carrying offline edits) is queued for offline reconciliation, which adds writer blocks lost to a merged agent deletion to that agent turn's change trail; Hocuspocus onStoreDocument (2 s debounce, 10 s maximum, and last disconnect) queues a checkpoint. hocuspocus-persistence.ts persistConnectionUpdate and storeHocuspocusDocument, domain/offline-reconciliation.ts

A failed admission closes the socket through the raw peer with 1013 writer-journal-admission-failed. Throwing alone is not enough: Hocuspocus swallows a thrown error's code, so only the direct peer close preserves it. WebSocket concurrency

Journal first. Novel content is durable before any Yjs apply, broadcast, or ack. If it were applied first, a crash or failed insert would leave other clients holding prose that no durable record contains, and the next cold load would silently lose it.

Reserved client IDs and the provenance namespace

Yjs client IDs 0 through 999 remain reserved for the provenance ingest guard; no undo writer owns client 999. Every server Y.Doc is built with createCollabYDoc, which redraws until its ID is outside that band. A writer frame carrying a struct from the band is rejected, the document is marked so the next room checkpoint is skipped (the rejected struct may still sit in memory), and an invariant event is emitted. If a client could author under a reserved ID, two writers would share one client ID, which breaks the Yjs assumption that one ID has one writer and would let a client forge server provenance. packages/prosemirror-schema/src/index.ts RESERVED_CLIENT_ID_MAX, hocuspocus-persistence.ts rejectReservedClientIdUpdate

The Y.Map __meridian_provenance_targets_v2 is the reserved provenance namespace. The server writes certified target-to-root lineage facts there, keyed by target client and clock, in each part’s own fresh-client transaction so metadata cannot couple independent review rows. Moved or restored prose keeps its original first-birth attribution. Old dev snapshots may retain the inert v1 array root; those facts are not read. A writer update that inserts into, deletes from, or anchors inside that map is rejected before append. A client able to edit it could rewrite whose prose is whose, and with it which edits count as swept writer work. domain/provenance.ts PROVENANCE_TARGETS_TYPE and validateClientUpdateAdmission

The WebSocket concurrency fence (LOCK-WS)

withDocument() on the live coordinator is an in-process mutex over coordinator callers. It does not stop Hocuspocus from applying a writer frame to the same Y.Doc while a coordinator callback is awaiting a database call. So any server-side apply that follows an await must re-check the live document and apply in one synchronous block with no await between them. agent-edit's applyCommittedUpdateWithRecheck is that block for response commits and revert; Apply settlement uses a full-state fingerprint compare plus the writer-ingress generation inside its completion fence. adapters/hocuspocus-coordinator.ts, packages/agent-edit/src/tool/mutation-commit.ts, domain/branch-push-transition.ts completeUnderFence, WebSocket concurrency

The review-room variant (writer edits in a Work draft)

A draft review room is an ordinary collaborative room; the writer is one more peer. Before frames are admitted, onConnect awaits the branch's live catch-up, so the room loads the same state the durable branch has and the writer's cumulative sync step 2 never meets a stale room. A stale room also catches up to the durable snapshot under the coordinator lock (origin branch-room-reconcile, which onChange skips). Admission then runs one sequence against one locked branch snapshot: the branch must be an active work_draft and the room must contain the snapshot; then containment, fresh authorship, late-peer recovery, and a snapshot compare-and-set plus a branch_write_journal row with source writer. Recovery handles a client that typed into text a rebase already changed: typing it cannot place exactly lands as its own paragraph beside its last known neighbour, and a deletion alone is reported unplaced and never written, so a reconnect that replays a delete set cannot erase retyped words. A refusal closes the socket with 4206 branch-closed (the branch is gone) or 4410 write-refused (terminal for this socket's writes); any other failure closes with 1013 branch-update-admission-failed and may reconnect. Branch rooms never re-persist in onStoreDocument; every branch mutation is already durable.

lib/yjs-ws-handler.ts admitBranchSync, domain/branch-coordinator.ts commitWriterUpdate, packages/agent-edit/src/diff/late-peer-recovery.ts, packages/contracts/src/protocol/ws-close.ts, hocuspocus-persistence.ts admitBranchWriterUpdate and storeHocuspocusBranch

5. The AI write path

An AI write is staged in agent-edit's runtime Y.Doc for the length of a model response, then committed in three phases. Where the commit lands depends on the thread's Work.

ModeChosen whenCoreLands in
Direct The chat's aiWriteMode is direct (Auto-apply), so draftOwner === null. This includes No Work. The live utility core The live journal and live room, at response commit
Draft aiWriteMode is draft The thread's thread-peer core The Work draft; live only after the writer's Apply

composition.ts (agentEdit: (context) => context?.draftOwner === null ? runtime.liveUtilityCore : agentEdit), ../threads/domain/thread-execution-context.ts

The three commit phases

  1. Preflight. Under the coordinator lock, capture what changed concurrently since the model's read. This feeds the echo the model sees; it never vetoes the write.
  2. Journal acceptance. Direct mode calls appendBatch on the live journal: one transaction that locks every touched document in sorted order, allocates one admission per document, inserts the agent journal rows and captures immutable edits and parts with their placements and reserved w<N> handles. Draft mode's journal only stages the entries in memory; their durable home is the branch commit in phase C.
  3. Apply. Under the coordinator lock, applyCommittedUpdateWithRecheck re-captures concurrency and applies the merged update in one synchronous block. In direct mode that target is the live room. In draft mode it is the thread peer, and the thread-peer coordinator then commits the peer's ordered segment updates into the Work draft (one snapshot compare-and-set plus one branch_write_journal row per segment, through admitCertifiedMutation when the write carries a semantic edit IR).

packages/agent-edit/src/tool/response-committer.ts, adapters/drizzle-journal.ts appendBatch, domain/branch-agent-edit.ts, domain/branch-coordinator.ts commitSegmentRows

Draft-mode commits run inside one Drizzle transaction per reply, with process-local effects (branch cache updates, watermarks, response ownership) enlisted as participants that commit or abort with it. A failed multi-document reply leaves nothing behind. Direct mode commits inside the live core instead. domain/thread-peer-core-pool.ts commitResponse, domain/response-transaction.ts, domain/response-write-finalizer.ts

After commit, finalizeResponseCommit records late-sweep and awareness notices, checkpoints each touched thread peer (draft mode), refreshes the markdown projection for each document (section 10), and runs the invisible-write check: words the reply wrote into draft text the writer had already discarded stay discarded, and the writer and the model's next turn are told (draft_write_invisible). Discard is a local edit, so the reply is never refused. domain/response-write-finalizer.ts, domain/draft-write-visibility.ts

Merges are trusted. Destructive effects become marks, receipts and trail evidence, never a veto on a valid Yjs merge. Revert and the writer's own Ctrl+Z are the recovery. Adding an approval gate here would refuse the writer's own instruction to the AI.

Settlement: how Apply reaches live

Every Apply (an item, some of its changes, or Apply all) is one staged, fenced batch so that warm and cold execution produce the same live document. Each text item is a content member: the change the writer saw merges into live's current text, and live text it replaced comes back in overrode. Draft bytes are never copied to live.

Admission freezes each item's input and plans against the live lock cut; one transaction durably writes the command, push lineage and settlement outbox; settlement replans every member against the document as it stands (staged bytes are never replayed); completion persists the live update, the reconcile row and the base patch under the document mutation lock, and applies to the live room only if its fingerprint still matches.

domain/draft-publication.ts, domain/draft-apply.ts, domain/branch-push.ts, domain/branch-push-transition.ts settleBatch, adapters/drizzle-pending-settlement.ts completeBatch, adapters/drizzle-draft-tree-step.ts

The base is never stored as bytes and replayed: the base patch and late-peer recovery both write as server client 1, so a staged delta replayed after a crash would collide on struct ids and Yjs would drop it silently. A patch computed under the lease at completion has nothing to collide with. The reconcile row exists because authored rows alone can omit causal dependencies of the merged state; it is coverage, not an author. A crash after the durable commit leaves a pending outbox row that the recovery lane (recoverPendingLiveSettlements, run by the change-trail worker) completes with the same code path; a batch blocks only on validated corrupt durable authority. Depth lives in settlement and change trail.

The change trail and receipts

  • Change trail. The sole durable publication record: one folded set of before/after block changes per turn (or one shared trail per thread), keyed by Yjs {clientID, clock} identity. It is written by settlement and by offline reconciliation. A direct-mode AI write does not write a trail on this checkout. adapters/drizzle-branch-push.ts persistRequiredTrail, domain/offline-reconciliation.ts, adapters/drizzle-change-trail-aggregate.ts
  • Trail dirty signals. Mutation transactions append to change_trail_dirty_log. The change-trail worker reconciles affected owners from durable journal cuts; its completion transaction consumes the signals and publishes derived changes. adapters/drizzle-change-trail-aggregate.ts, adapters/change-trail-worker.ts
  • Receipts. Live and draft receipt actions use immutable edits and parts with their current placements. A part's placement is pending (on a text branch), live, or discarded. Model revert and failed-reply rollback compute forward inverse edits; trail evidence remains read-only. adapters/drizzle-document-edits.ts, domain/turn-inverse-service.ts

6. The journal and reconstruction

The live journal is an append-only list of Yjs updates per document, plus checkpoints that cache a prefix of it. A live Y.Doc is always "the newest checkpoint plus every later row of the same generation".

TableHolds
document_yjs_updatesOne row per admitted update: bytes, authority ID, generation, admission sequence, batch ordinal, origin (human, agent, system, reconcile), actor user or turn, authoring response.
document_yjs_checkpointsFull encoded state at up_to_seq, its authority generation, and an attribution manifest that freezes first-birth attribution so compaction cannot lose it.
document_yjs_headsThe authority head, plus the schema stamp, latest checkpoint and state vector, and retired_through_seq: the highest row compaction has deleted in this generation.
document_edits, document_edit_partsImmutable edit identity and part bytes, with placement on each part; retained independently of journal compaction.

packages/database/src/schema/yjs.ts, packages/database/src/schema/document-edits.ts

A writer's typing produces roughly one row per keystroke; row counts are not semantic edits. Reconnect frames the room already contains are acknowledged without a row.

Where checkpoints come from

  • Seed. A new document's first content is installed as an up_to_seq = 0 checkpoint with no journal rows. Seeding is initialize-only; a later attempt on a document with any admission or checkpoint is a successful no-op. adapters/drizzle-journal.ts createServerDocumentLifecycle, domain/markdown-document.ts seedFromMarkdown
  • Room store. Hocuspocus onStoreDocument queues the room's authority binding. After the caller's transaction commits, the worker captures a durable cut and writes it (dropped on rollback or when the generation was retired), one queued request per document, newest wins. A checkpoint at a cut no newer than the existing one is skipped. hocuspocus-persistence.ts storeHocuspocusDocument, adapters/drizzle-journal.ts captureCheckpoint and storeCheckpoint
  • Explicit. CollabDomain.checkpoint(documentId, reason). checkpoints.ts
  • Compaction. journal.compact(docId, before) folds the contiguous prefix of current-generation rows older than before into a compact checkpoint (or folds nothing when an ordinary checkpoint already covers them), deletes those rows only, and raises retired_through_seq in the same transaction. Immutable forward edit parts retain inverse authority. It is implemented and tested, but no production scheduler calls it on this checkout, so live rows are never deleted. adapters/drizzle-journal.ts compact

The rule for every checkpoint writer: it may under-claim but must never over-claim. A row at or below up_to_seq is never replayed again, so if the state lacked it the row is lost; a row above it replays harmlessly on top. So no writer encodes the room. Seed, room and explicit writers all persist an opaque CapturedCheckpointCut that only the journal adapters mint. Under the document mutation lock, journal.captureCheckpoint records only references: the current-generation base checkpoint and the last committed row, including admissions Hocuspocus has not yet applied to the room. The lock is released before any bytes are read. Persistence then replays base plus suffix outside the lock, and under its own lock rechecks the generation and that compaction has not retired the suffix. A stale cut is dropped (an explicit checkpoint returns stale_generation). A cut whose suffix compaction retired fails the write: the room worker emits checkpoint.failed, and the next store captures afresh. Unresolved Yjs dependencies refuse the cut. domain/checkpoint-cut.ts, adapters/drizzle-checkpoint-capture.ts, adapters/drizzle-journal.ts storeCheckpoint, checkpoints.ts checkpoint

adapters/document-loader.ts loadDocumentState, adapters/drizzle-journal.ts read, adapters/hocuspocus-coordinator.ts applyMissing, domain/branch-coordinator.ts materialize and runWithRetry

The coordinator heal matters: every withDocument call opens the room, re-reads the journal, and applies whatever durable rows the room is missing before the callback runs. A row that was journaled but never applied to a warm room therefore heals on the next server touch, and a cold room simply replays it.

Bounded journal reads

journal.read takes optional since and until row bounds; with until it picks the newest checkpoint at or before that row so a historical read never sees later edits. The checkpoint also stays below since so inclusive retained rows are not hidden. Unbounded reads return the durable watermark even when compaction leaves no update rows. Inverse planning reads immutable edit parts, independently of journal compaction. Settlement rebuilds its historical "final pre-push" document from the outbox's own lock cut plus joined updates, never from the current room.

adapters/drizzle-journal.ts read, domain/branch-push-transition.ts materializeFinalPrePush

7. Branches: rebase, Apply, Discard

Branch mechanics are covered in depth by branch model and records and the product shape by the draft / live model. The points below are the ones that change how you reason about edits here.

  • The review is a diff against a base. A text branch keeps review_base beside prosemirror. The client projects the room into changes (projectReview in @meridian/agent-edit/diff), one red/green unit each, and an item has changes when the two fragments differ (has_effect on the branch row). There are no per-edit accept surfaces and no closure classes: a change is whatever the diff shows. packages/agent-edit/src/diff/, domain/draft-rebase.ts
  • Rebase is a three-way merge, not replication. Live edits reach the draft as a merge of base, live and draft, so the writer's and the AI's pending edits survive a live edit and the base advances to live. A late peer's stale frame is recovered as paragraphs of its surviving typing, never by replaying its stale deletions; no rebase cuts are retained. domain/draft-rebase.ts, packages/agent-edit/src/diff/late-peer-recovery.ts
  • Apply is content Apply. The writer's Apply of an item (apply_items) or of named changes (apply_changes) carries the Y.snapshot of the room frame it acted on when the client has one (otherwise the request freezes at staging), so it applies what the writer saw, not words typed since. The change is a content merge into live's current text (rebase), not Yjs replication; live text it replaced returns in overrode as one dismissible notice, never a gate. Live text moving never refuses; only a live rename, move or reveal since the list was read answers stale (the locationToken). A created document is revealed with the content its Apply asked for. Apply never closes the draft or an edited item; the base patch just moves the applied change into the base. packages/contracts/src/drafts/review.ts, domain/draft-publication.ts applyItems, domain/draft-apply.ts, domain/draft-commands.ts
  • Discard has three shapes. Local Discard (one change, Discard draft in a review, the strip, a Work row) is an ordinary writer edit in the room that sets the chosen changes back to the base. It sends no command, closes nothing, and Ctrl+Z (or the row's Undo) restores it. Item Discard (discard_items) closes one item and is sent only for whole-item items: a created, binary or live-deleted document. Discard all (discard_draft) closes every branch and the draft. The Discard kernel is the only branch closer; an item's text is never reset from live. domain/draft-discard.ts, adapters/drizzle-draft-discard.ts
  • A branch has no generation. Its room is branchRoomName(draftBranchId), returned by the server. An empty text branch stays active after local Discard or Apply. A closed branch gets a fresh id on the next write, which is the only remount. Existence is item metadata (200 versus 404 gone) plus the server closing the room with 4206. packages/contracts/src/protocol/yjs-ws.ts branchRoomName, adapters/hocuspocus-binding.ts
  • Listing is one predicate. An item is listed when it is a created node, or its active text branch has has_effect or an inverse hold. Lists, counts, the Work page and Apply all read the same SQL relation, and every branch write goes through one projection-wrapped writeBranchState. domain/draft-review-items.ts, adapters/drizzle-branch-push.ts, adapters/drizzle-branch-state.ts

Echo attribution

When the model writes, its result echoes what others changed in the same blocks since its read. In draft mode the thread-peer coordinator builds that echo from durable evidence only: Work-draft journal rows after the thread's concurrent-journal watermark, plus live journal rows after the live sequence captured at pull time. It replays them over the peer's baseline and attributes each touched block to an agent turn or a writer by block coverage; whatever the rows do not explain becomes an unattributed human residual. Memory-only maps are never an attribution source, so a restarted process echoes the same thing. The watermark advances only when the surrounding branch write commits.

domain/branch-agent-edit.ts concurrentUpdatesSince and partitionConcurrentUpdates, domain/branch-update-attribution.ts

8. Forward-turn inverses

Collab owns durable revert and failed-reply rollback through turn-inverse-service.ts. Immutable edit parts capture each forward operation and its inverse. Revert is the model's tool: it writes into the thread's current destination (the active draft's text branch, or live in direct mode) as an ordinary journal row with pending parts, so it shows as a change the writer applies. Rollback keeps a failed reply's order and skips parts already discarded. Certified aliases connect displaced identities. A part's placement is pending (branch and row), live (sequence) or discarded; a blocking hold (document_branches.blocking) keeps an item reachable while a revert is held. There is no card Undo or Redo, no reconstruction reversal engine, mutable reversal history, or reserved undo client; the writer's undo is Ctrl+Z in the editor.

Full policy and persistence contracts: turn inverses.

9. Schema fence and repair

A Y.Doc's bytes only make sense under the ProseMirror schema that wrote them. The fence stops a client or server from replaying a document under a schema that would corrupt it; repair keeps a document usable when content does not fit.

The fence

  • Heads and branch rows carry a packed (major, minor, patch) stamp, raised with greatest() so a rolled-back server can never lower it.
  • On connect, per connection (Hocuspocus deduplicates loads): if the server's major differs from the head's, close 4407 document-schema-stale; else if the client's (major, minor) is behind the head, close 4406 client-schema-superseded. Patch never gates. An unstamped head passes.
  • Every journal read asserts the head's major matches the server and throws DocumentSchemaMajorMismatchError otherwise; the load hook turns that into the same 4407 close as a race backstop.

Coherence and repair

  • One engine. Every seed, write and serialization goes through domain/markdown-document.ts, which resolves the document's filetype first (markdown codec for documents; one verbatim code_block for code). Hand-built fragment content could produce state the client's schema would normalize away.
  • Serialization never mutates its input. Projection runs on a private gc: false clone. If normalization changes that clone, a collab.schema serialize.anomaly_observed event is emitted (schema version and counts, never prose) and serialization continues.
  • Client repairs merge. When y-prosemirror repairs invalid content in the editor, the repair is an ordinary writer update that goes through the path in section 4; the client's schema repair witness reports it to the writer and never blocks it. apps/app/src/core/editor/schema-repair-witness.ts

11. The composition root

createCollabDomain in composition.ts is wiring only: it builds adapters, builds domain services with required dependencies, and returns the facade. Behavior lives in domain/; collab-facade.ts only spreads the service groups into CollabDomain. The order of construction follows the dependency graph.

  1. Persistence and live transport. The Drizzle journal and lifecycle; a late-bound Hocuspocus binding (the gateway binds itself after construction); the live coordinator over it.
  2. Branches. One BranchCriticalSections (the only owner of the branch mutex, shared by store, coordinator, push, review and discard so lock order stays global); the branch store, coordinator and pull service.
  3. Runtime. createAgentEditRuntime builds the markup codec exactly once with the injected DocumentLinkScopes, the schema-aware markdown engine, and the live utility core, each spelling links and image sources through the operation's prepared link scope. A second mdxCodec(...) elsewhere would spell stored hrefs instead of current paths.
  4. Settlement and Apply. Pending-settlement store, push-commit store, change-trail writer, writer-ingress binding (bound to the Hocuspocus persistence barrier once that exists), push service, the draft publication (content Apply), tree step and Discard kernel.
  5. AI cores. The thread-peer core pool over the live utility core, branch services and the response-transaction hooks.
  6. Transport persistence. Hocuspocus persistence wired to the journal, the authority-generation reader, offline reconciliation, and scheduleLivePull.
  7. Read models and commands. Response finalizer, Work-draft review service, effective reader, checkpoint service with authority-generation replacement, receipt lineage, turn inverse service; then the facade, whose agentEdit(context) selects the core per call.

Optional notices and the thread-context resolver are replaced by declared stubs in one place (adapters/declared-stubs.ts) instead of optional fields that would let a path silently skip a required operation. The in-memory composition (adapters/in-memory/composition.ts) builds the same interfaces for tests. Rules for this file are in CONTEXT.md.
