The Draft / Live Model

One document, two surfaces, one consent point. Everything in the system merges automatically (draft-mode AI edits into the draft, live edits into the draft) except a single edge: promoting the draft into live. That edge is Apply, and it belongs to the writer. Each chat owns its write mode; a chat in auto-apply (direct) mode writes straight to live, whatever its Work's default or its sibling chats do.

The two surfaces

Both surfaces are real Y.Docs mounted by the same editor with an explicit EditorMountIdentity — the surface is a construction fact, not a prop that drifts.

LiveReview (draft)
What it is The manuscript. Canonical journal (document_yjs_updates). The proposal. One Work-draft branch per (documentId, workId).
Who writes The writer and other live sessions, plus the AI of a chat in direct (auto-apply) mode. AI peers of draft-mode chats push every write here; live content pulls in continuously.
Annotations Peer marks — ephemeral session overlay (markerStore). Inline review decorations from the durable review model.
Leaving it — Apply (publish whole branch) or Discard (by discard class).

Everything below the gate is automatic

  • Draft-mode AI writes to the branch. createBranchAgentEditCoordinator gives a draft-mode thread no path to live. A chat in direct mode (aiWriteMode: "direct") routes AI writes to the live core instead (composition.ts). Either way there is no per-edit accept, no veto, no sweep negotiation.
  • The draft continuously pulls from live. branch-pulls.ts (scheduleLivePull / flushLivePull) merges live updates into the draft. Room admission triggers a pull; open rooms receive pull deltas without reconnecting. If another session edits live, the edit shows up in the draft — peer marks riding along.
  • Pulls arrive as chunks, attributed with marks — not cursors. Yjs presence is room-scoped by design; a cursor for someone editing a different surface would be a ghost. A chunked pull is a unit you can mark with provenance. Keystroke streaming has no boundary to hang a mark on: it reads as haunted text, not collaboration. Live enough to trust, chunked enough to read.
  • Merging always succeeds. CRDTs never refuse a merge — that is the point of them. Rejection is not a Yjs concept; it exists only at the one application-layer edge below.

The one consent point: Apply

Apply is consent. Clicking it means the writer accepted that each selected item's whole current branch, including writer edits made after preview, replaces live, with its tree change (reveal, restore, rename back). Within an item there is no partial apply and no machine arbitration of meaning; an item whose path is taken is held. Proposal cards offer selective Discard only, grouped by server-vended discard class.

The writer's protection is not a veto layer. It is two things:

  1. Seeing what Apply will do — the review surface, and a planned live-vs-draft diff mode (#421).
  2. Refusing a stale Apply (below).

A stale Apply is refused, never merged on the writer's behalf. Each item carries the tokens its review rendered (location version, the live text's full-state fingerprint, the branch generation); Apply compares them under the batch's locks and answers stale when any moved, so the writer looks again. A deletion moves the fingerprint, which a state vector would miss. This is item and per-change Apply; whole Apply publishes the current branch. Pulls (live to draft) need no consent. (domain/draft-publication.ts, adapters/drizzle-draft-tree-step.ts)

The durable record

  • Change trails are the sole durable publication record. Settlement keeps exact authored rows plus a canonical reconciliation row, so cold replay matches the live merge.
  • A completed turn rests as one compact receipt. Expansion shows every trail change in ordinal order with Before/After. Receipt-level Undo/Redo is the sole AI reversal authority; mark popovers are read-only evidence.
  • Runtime state is memory-only. Restarts cold-reconstruct from the live journal plus each branch's checkpoint and tail rows.

What this model replaced

Deleted machinery, and why
  • The conflict veto — could refuse a valid Yjs merge. Refusing merges is anti-CRDT; consent moved to the Apply edge instead.
  • Durable writerImpact classification — duplicated live-mark meaning; a second source of truth for the same fact.
  • Popover Restore — a second reversal authority competing with receipt Undo.
  • Publish-time rebase — rejected on product grounds: it would have the machine arbitrate meaning. Preserved as a rejected alternative in the work archive (archive/work/draft-simplify/design/publish-time-rebase.md).
  • Per-edit accept surfaces and sweep fan-out — made routine edits feel exceptional; consent belongs at one edge, not smeared across every change.

The recurring disease was two sources of truth for one fact; the recurring cure was one mechanism, enforced by types and keys rather than prose.

Boundaries that must hold

EdgeRule
live → draftNo consent gate. Continuous and automatic; a pull merges whenever it runs. It waits while an Apply of the same document is settling, and keeps running while the Work is archived, so the draft applies cleanly after unarchive (see the archive contract in CONTEXT.md).
draft → liveOnly via Apply. The single consent-bearing promotion. Item and per-change Apply refuse a stale render; whole Apply has no live-head guard yet (#420).
AI → liveDirect mode only. A draft-mode chat's AI writes to its Work's branch, always. The mode is the chat's, never the Work's.
PresenceRoom-scoped. No cross-surface cursors; cross-surface provenance uses marks.
