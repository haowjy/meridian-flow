The Draft / Live Model

One document, two surfaces, one consent point. Everything in the system merges automatically (draft-mode AI edits into the draft, live edits into the draft) except a single edge: promoting the draft into live. That edge is Apply, and it belongs to the writer. A Work in direct mode has no draft: its AI writes go straight to live.

The two surfaces

Both surfaces are real Y.Docs mounted by the same editor with an explicit EditorMountIdentity — the surface is a construction fact, not a prop that drifts.

LiveReview (draft)
What it is The manuscript. Canonical journal (document_yjs_updates). The proposal. One Work-draft branch per (documentId, workId).
Who writes The writer and other live sessions, plus the AI when its Work is in direct mode. Draft-mode AI thread peers push every write here; live content pulls in continuously.
Annotations Peer marks — ephemeral session overlay (markerStore). Inline review decorations from the durable review model.
Leaving it — Apply (publish whole branch) or Discard (by discard class).

Everything below the gate is automatic

  • Draft-mode AI writes to the branch. createBranchAgentEditCoordinator gives a draft-mode thread no path to live. A Work in direct mode (aiWriteMode: "direct") routes AI writes to the live core instead (composition.ts). Either way there is no per-edit accept, no veto, no sweep negotiation.
  • The draft continuously pulls from live. branch-pulls.ts (scheduleLivePull / flushLivePull) merges live updates into the draft. Room admission triggers a pull; open rooms receive pull deltas without reconnecting. If another session edits live, the edit shows up in the draft — peer marks riding along.
  • Pulls arrive as chunks, attributed with marks — not cursors. Yjs presence is room-scoped by design; a cursor for someone editing a different surface would be a ghost. A chunked pull is a unit you can mark with provenance. Keystroke streaming has no boundary to hang a mark on: it reads as haunted text, not collaboration. Live enough to trust, chunked enough to read.
  • Merging always succeeds. CRDTs never refuse a merge — that is the point of them. Rejection is not a Yjs concept; it exists only at the one application-layer edge below.

The one consent point: Apply

Apply is consent. Clicking it means the writer accepted that the current draft — the whole branch, including writer edits made after preview — replaces live. There is no partial apply, no machine arbitration of meaning. Proposal cards offer selective Discard only, grouped by server-vended discard class.

The writer's protection is not a veto layer. It is two things:

  1. Seeing what Apply will do — the review surface, and a planned live-vs-draft diff mode (#421).
  2. Refusing a stale Apply: decided, not yet built (below).
Decided, not built: refuse a stale Apply (#420)

Not implemented. Apply takes only { draftId } and pushes the branch against whatever live holds; tracked in #420. The decided rule: Apply consents only to replacing the live the writer was looking at. If live advanced past the draft's rendered pull state at the moment of Apply, the server refuses (git push non-fast-forward semantics). The planned mechanism:

  1. Type: Apply requires a branded expectedLiveHead token. Calling apply without declaring a base is a compile error.
  2. Source: the token is server-minted from the pull bookkeeping the draft already maintains; the client echoes the watermark it rendered. One source of truth for "what has the draft seen."
  3. Check: a fast-forward guard (expectedLiveHead vs current head) inside the apply transaction, under the same serialization that orders live writes. Refusal is total — nothing partially applied.
  4. Recovery is automatic: refusal → pull refreshes the draft → AI re-proposes → writer applies again. The refusal is a retry loop that resolves itself; the writer's only job is to look and click again.

Detection is a state-vector comparison (live's SV ≤ draft's pulled SV ⇔ "draft is up to date"); refusal is application-layer because CRDTs cannot refuse. Pulls (live→draft) are never gated — do not generalize the guard onto the pull path.

The durable record

  • Change trails are the sole durable publication record. Settlement keeps exact authored rows plus a canonical reconciliation row, so cold replay matches the live merge.
  • A completed turn rests as one compact receipt. Expansion shows every trail change in ordinal order with Before/After. Receipt-level Undo/Redo is the sole AI reversal authority; mark popovers are read-only evidence.
  • Runtime state is memory-only. Restarts cold-reconstruct from the live journal plus branch state/journal rows.

What this model replaced

Deleted machinery, and why
  • The conflict veto — could refuse a valid Yjs merge. Refusing merges is anti-CRDT; consent moved to the Apply edge instead.
  • Durable writerImpact classification — duplicated live-mark meaning; a second source of truth for the same fact.
  • Popover Restore — a second reversal authority competing with receipt Undo.
  • Publish-time rebase — rejected on product grounds: it would have the machine arbitrate meaning. Preserved as a rejected alternative in the work archive (work/draft-simplify/design/publish-time-rebase.md).
  • Per-edit accept surfaces and sweep fan-out — made routine edits feel exceptional; consent belongs at one edge, not smeared across every change.

The recurring disease was two sources of truth for one fact; the recurring cure was one mechanism, enforced by types and keys rather than prose.

Boundaries that must hold

EdgeRule
live → draftNever gated. Continuous, automatic, always merges.
draft → liveOnly via Apply. The single consent-bearing promotion. The stale-Apply guard (#420) is not built yet.
AI → liveDirect mode only. A draft-mode Work's AI writes to the branch, always.
PresenceRoom-scoped. No cross-surface cursors; cross-surface provenance uses marks.
