The Draft / Live Model

One document, two surfaces, one consent point. Everything in the system merges automatically (draft-mode AI edits into the draft, live edits into the draft) except a single edge: promoting the draft into live. That edge is Apply, and it belongs to the writer. Apply is a merge: the change lands in live's current text, and anything it replaced is reported, never refused. Each chat owns its write mode; a chat in auto-apply (direct) mode writes straight to live, whatever its Work's default or its sibling chats do.

The two surfaces

Both surfaces are real Y.Docs mounted by the same editor with an explicit EditorMountIdentity: the surface is a construction fact, not a prop that drifts. A draft's Y.Doc carries two fragments, the prosemirror text the writer and the AI edit and a server-owned review_base: live's text as of the last time the draft caught up (base_revision). The review is the difference between them.

LiveReview (draft)
What it is The manuscript. Canonical journal (document_yjs_updates). The proposal. One text branch per (documentId, draftId), shown as a diff against its base.
Who writes The writer and other live sessions, plus the AI of a chat in direct (auto-apply) mode. AI peers of draft-mode chats push every write here; live content rebases in continuously; the writer edits it directly, including local Discard.
Annotations Peer marks, an ephemeral session overlay (markerStore). Changes: the review projection of base against draft (projectReview), one red/green unit each.
Leaving it Apply (all of an item, or chosen changes), local Discard (a writer edit), item Discard, Discard all.

Everything below the gate is automatic

  • Draft-mode AI writes to the branch. createBranchAgentEditCoordinator gives a draft-mode thread no path to live. A chat in direct mode (aiWriteMode: "direct") routes AI writes to the live core instead (composition.ts). Either way there is no per-edit accept, no veto, no sweep negotiation.
  • The draft continuously rebases onto live. branch-pulls.ts schedules the catch-up and draft-rebase.ts performs it: a three-way content merge of base, live and draft, so the writer's and the AI's pending edits survive a live edit and the base advances to live. Room admission awaits one before frames are admitted; open rooms receive the delta without reconnecting.
  • Discard is the writer's edit. Discarding a change, a draft or a Work row sets the text back to the base inside the room, under the editor's own origin. It sends no command and closes nothing; Ctrl+Z restores it. A reply still writing into text the writer discarded merges like any peer, and both the writer and the model are told which words landed in discarded text.
  • Merging always succeeds. CRDTs never refuse a merge, that is the point of them. Rejection is not a Yjs concept; the one application-layer edge is below, and it reports instead of refusing.

The one consent point: Apply

Apply is consent. Clicking it means the writer accepted that the change (or every change of the item) merges into live. The request carries a snapshot of the room frame the writer acted on, so Apply applies what the writer saw, not words typed since. The server merges the change into live's current text, moves it into the base, and reports the live text it replaced as overrode: one dismissible notice, never a gate. A tree change rides along: a hidden create is revealed, a live-deleted document restored, and an item whose path is taken is held.

The writer's protection is not a veto layer. It is two things:

  1. Seeing what Apply will do: the review surface shows each change as a diff against the base the writer's live text produced.
  2. Being told what it replaced, and Ctrl+Z, because Apply is itself a live edit.

Live text moving never refuses an Apply. Only a live rename, move or reveal between the list and the click answers stale, because the item's location token is the one freshness check left; the review refreshes and the writer looks again. After Apply the applied change is part of the base, so the item lists only if the draft still differs from it; an edited item whose changes are all applied simply has no changes left, and its room stays. The durable record

  • Change trails are the sole durable publication record. Settlement keeps a canonical reconciliation row, so cold replay matches the live merge.
  • The model's recovery is revert. It writes into the thread's current destination as an ordinary pending change the writer applies, and a failed reply rolls back. Mark popovers are read-only evidence.
  • Runtime state is memory-only. Restarts cold-reconstruct from the live journal plus branch state and journal rows.

Deliberately absent

  • A conflict veto. Refusing a valid Yjs merge is anti-CRDT. Consent sits at the Apply edge, and the edge reports.
  • Publish-time arbitration of meaning. The server never picks between the writer's words and live's; Yjs merges and the notice reports (rejected alternative in the work archive, archive/work/draft-simplify/design/publish-time-rebase.md).
  • Per-edit accept surfaces. Routine edits are not exceptional; consent belongs at one edge, not smeared across every change.

The recurring disease was two sources of truth for one fact; the recurring cure was one mechanism, enforced by types and keys rather than prose.

Boundaries that must hold

EdgeRule
live → draftNever gated. Continuous, automatic, always merges.
draft → liveOnly via Apply. The single consent-bearing promotion, a merge that reports what it replaced.
AI → liveDirect mode only. A draft-mode chat's AI writes to its Work's branch, always. The mode is the chat's, never the Work's.
DiscardLocal Discard is a writer edit. Only whole-item items and Discard all send commands, and only they close branches.
PresenceRoom-scoped. No cross-surface cursors; cross-surface provenance uses marks.
